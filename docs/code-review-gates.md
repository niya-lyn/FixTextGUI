# FixText 代码评审门禁

本文件是 M0–M5 全部任务卡的**固定检查项**清单，任一条不通过不得过审。
条目来源：《FixText 第一版功能范围与开发排期》3.5「重写注意事项」。

适用范围：所有涉及 PHP → Python 重写的提交，尤其 T0.2（词库迁移）、T1.6（六处闭包重实现）、T0.3（Go 引擎集成）、T5.1（全量回归）。

---

## 一、四条固定检查项（3.5 原文要求）

### G1 · PHP 闭包重写必须单独测试，不依赖 JSON 序列化结果

**要求**：6 处 PHP 闭包的**运行时行为**必须在 Python 侧重写实现，并且**单独测试**；不得以「导出的 JSON 结果一致」代替对闭包行为的验证。

**为什么**：闭包的运行时行为（捕获变量的时机与作用域、`use` 引用传递、`preg_replace_callback` 的偏移推进、闭包在排序器中的比较语义）在 JSON 序列化中会丢失。JSON 只能证明「某个输入下最终输出相同」，无法证明闭包内部逻辑被正确重写——一旦输入分布变化，偏差即暴露。

**评审动作**（提交需同时附）：

- 说明待验证的闭包在 PHP 侧的完整语义：入参、捕获变量、可变状态（引用 vs 值）、副作用、边界条件；
- 对应的 Python 实现位置，以及**独立单测用例**（不经过 JSON / 词库导出链路，直接构造闭包输入调用被测函数）；
- 用例须覆盖：正常路径、边界值、捕获变量被修改的情形、多次调用的状态隔离；
- 若某处闭包行为确无法在 Python 侧等价复现，须在 MR 描述中显式列出差异、影响范围与风险，不得静默改语义。

**不通过示例**：只给一份「迁移前后 JSON 全等」的对比报告；或测试用例直接读 JSON 词库文件再断言输出。

---

### G2 · strictMap 瑕疵按数据清洗处理，不作为代码缺陷阻塞迁移

**要求**：`strictMap` 中「mark 作为键而非值」的问题，定性为**数据清洗**问题，在迁移脚本 / 数据层修复；不得因此把迁移判为代码缺陷而阻塞推进，也不得在代码里塞特判补丁去兼容脏数据。

**评审动作**：

- 确认处理位置在**数据清洗环节**（迁移脚本或词库数据文件），而非业务代码中的 `if 特例`；
- 清洗规则须写明：识别条件、清洗后的目标结构、被清洗条数的统计口径与结果；
- 清洗结果须可复现——重跑迁移脚本能得到同一份数据；
- 代码侧不得出现针对该瑕疵的隐式兜底（如静默跳过异常键、`try/except` 吃掉 KeyError 后继续）。

**不通过示例**：在替换引擎里写 `if key == 'mark': continue`；或清洗没有统计与留痕，无法证明做了这件事。

---

### G3 · 迁移脚本与重写工具链必须显式检测 PHP 闭包并报警，禁止静默降级

**要求**：任何解析 PHP 词库 / 配置的脚本、任何将 PHP 结构翻译为 Python 的工具，**必须显式检测 PHP 闭包**（如 `function (...) { ... }`、`fn (...) =>`、`use (...)` 捕获），一旦遇到就**报警并中止或明确标记该项未迁移**。

**为什么**：闭包一旦被当作普通值序列化，就会静默变成字符串或 `null`，产出看似成功、实则丢失逻辑的产物——这类失败最难发现，也最容易过审。

**评审动作**：

- 脚本中须存在显式的闭包检测分支（正则或语法解析均可），并在命中时非 0 退出或输出结构化告警条目；
- 告警信息须包含：文件、变量名 / 键路径、行号（可得时）、闭包片段特征；
- 必须**有测试证明报警会真的触发**（构造含闭包的样例输入，断言报警产生且流程不静默通过）；
- 禁止 `try/except: pass` 式的兜底降级；禁止把无法解析的值默认成空值后继续。

**不通过示例**：迁移日志显示「全部成功」，但其中有变量实际是闭包且被写成 `null`；或检测到闭包只打了 `logging.debug` 就继续跑完。

---

### G4 · 禁用 flashtext / iter_long

**要求**：引擎实现不得使用 `flashtext`，不得使用 `pyahocorasick` 的 `iter_long`。

**依据（P0 验证结论）**：`flashtext` 实测 win_rate = 0，连排关键字会漏替；`pyahocorasick.iter_long` 失败时吞字符，命中率异常（99.03% 窗口）。

**允许的做法**：`pyahocorasick` 的 `iter`（全量匹配）+ 自行实现贪心选路；Go 引擎 `strings.NewReplacer`。

**评审动作**：

- 依赖清单中不得出现 `flashtext`；
- 代码中不得出现 `iter_long` 调用；
- 引擎相关 MR 须附性能 / 正确性对照证据（与 Go 引擎逐字节比对，或与基线集对照）。

**自动化支撑**：`python scripts/check_gates.py` 会扫描全仓并拦截上述两类用法，已在 CI 中执行（本仓库 `tests/test_gate_checker.py` 反向验证了脚本确实能拦住违规写法）。

## 二、骨架阶段的额外结构约定

以下条目不属于 3.5 四条，但为保障后续任务卡可验证，一并纳入评审：

| 编号 | 约定 | 校验方式 |
|-|-|-|
| S1 | `core` / `engine` 层不得导入 PySide6，业务逻辑须可在无界面环境单测 | `scripts/check_gates.py` 自动拦截 |
| S2 | 用户原始文件不被修改，所有写操作落在用户数据目录（承接 2.3 只读保护） | 代码评审 + T4.4 自动化校验 |
| S3 | 错误提示不得直接暴露堆栈 / 命令行输出（承接 2.3 人话错误） | 代码评审 + T2.4 |
| S4 | 新增依赖须说明用途，并确认不引入 G4 禁用项 | 依赖清单评审 |

## 四、与 CI 的关系

`python scripts/ci.py` 一键执行 lint → format-check → gates → tests 四个环节，其中 `gates` 环节即本文件 G4 与 S1 的自动校验。

G1、G2、G3 属于**产物级核验**：它们是针对具体迁移脚本与闭包实现的检查，骨架阶段（T0.1）尚无相应产物，因此只能作为评审登记项存在。对应产物出现时（T0.2 迁移脚本、T1.6 闭包重实现），这三条转为必查，并须在 MR 中附测试证据。
