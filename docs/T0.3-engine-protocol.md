# T0.3 Go 引擎集成层 · 接口文档

任务卡：《FixText 第一版功能范围与开发排期》T0.3b Go 引擎集成层
协议版本：`fixtext-engine/1`
实现源：`src/fixtext/engine/{protocol,client,builder,errors}.py`（本文档以这四个模块为准，字段名、默认值、校验口径均与之逐条对齐）

本层只做「把 Go 引擎当成一个子进程调起来」这件事：**参数校验、临时工作区隔离、结果交付、错误码归类**。
替换语义（`strings.NewReplacer` 的首胜/最长匹配、两趟替换）全部由 Go 引擎负责，Python 侧不复制一份语义——这是与 M1 Python 引擎的分界线。

---

## 一、两层协议

集成层要同时满足两套契约，缺一不可：

| 层 | 契约 | 稳定性 | 谁定义 |
|-|-|-|-|
| 进程级调用契约 | `replace_by_go <目标文件> <替换前.json> <替换后.json> <替换次数>` | 由上游 Go 源码写死，**集成层不得修改** | `go_src/replace_by_go.go` |
| 集成层请求/响应 | `EngineRequest` → `EngineResponse` | 本层定义的稳定契约，改动需升 `PROTOCOL_VERSION` | `protocol.py` |

### 1.1 进程级调用契约（不可改）

```
replace_by_go <目标文件> <替换前.json> <替换后.json> <替换次数>
```

| 位置 | 参数 | 类型 | 语义 |
|-|-|-|-|
| `argv[1]` | 目标文件 | 路径 | 待替换文本；**引擎原地改写**（`os.WriteFile` 回写同一路径） |
| `argv[2]` | 替换前.json | 路径 | JSON 字符串数组，与 `after` 等长 |
| `argv[3]` | 替换后.json | 路径 | JSON 字符串数组 |
| `argv[4]` | 替换次数 | 正整数 | 整串替换执行几趟；`count=2` 是生产语义（链式收敛） |

约束（来自 Go 源码 `parseArgs`）：`len(os.Args)` 必须**恰好等于 5**，多传少传都直接报「参数数量错误」。

**输出约定**

| 通道 | 内容 | 判定 |
|-|-|-|
| stdout（成功） | `✓ 替换完成，共执行 N 次替换`（N = 请求的 count） | 集成层按前缀 `✓ 替换完成，共执行 ` 解析并**核对 N 是否等于请求值**，不符即 E1005 |
| stderr（失败） | `错误: <具体原因>` | 退出码 1，集成层按文案归类成 E22xx / E21xx / E24xx / E2301 |
| 退出码 | 0 = 成功；1 = 失败 | 非 0 一律走错误分支，不读 stdout 当结果 |

**为什么必须核对 N**：退出码 0 只能证明进程没崩，不能证明它真做了请求次数的替换。协议要求把「次数」也纳入校验，避免引擎被替换成空实现后静默通过。

### 1.2 只读保护（承接排期 2.3）

引擎是**原地改写**语义，直接拿调用方的原文件去跑，一旦中途失败原文件就已被部分改写。因此：

- `InputMode.FILE` / `MEMORY` + `OutputMode.MEMORY` / `FILE`：集成层**永远先复制到一次性临时目录**（`tempfile.mkdtemp(prefix="fixtext-engine-")`），引擎只碰临时副本，调用后整个目录删除；**原始文件字节不变**。
- `OutputMode.IN_PLACE`：唯一例外，调用方显式 opt-in。实现为先写 `<原文件>.fixtext-tmp` 再 `os.replace()` 原子替换，避免写到一半留下半个文件；且要求 `input_mode == FILE`（MEMORY 输入没有"原文件"可覆盖）。

## 二、集成层数据契约

### 2.1 常量

| 名称 | 值 | 说明 |
|-|-|-|
| `PROTOCOL_VERSION` | `fixtext-engine/1` | 请求缺省携带，响应原样回显；请求带了别的版本即 E2301 |
| `ENGINE_SUCCESS_PREFIX` | `✓ 替换完成，共执行 ` | 与 Go 源码 `fmt.Printf` 逐字一致，由 `tests/test_engine_protocol.py` 断言 |

### 2.2 `RuleSet` —— 词库输入

| 字段 | 类型 | 必填 | 说明 |
|-|-|-|-|
| `before` | `list[str]` | 是 | 替换前字符串数组 |
| `after` | `list[str]` | 是 | 替换后字符串数组，**长度必须与 `before` 相等** |
| `source` | `str` | 否（默认 `"memory"`） | 来源标记，仅用于留痕与报错定位；`from_files` 会填成 `before.json+after.json` |

校验口径**与 Go `loadRules()` 完全一致**，在构造时（`__post_init__`）立刻执行：

| 检查 | 错误码 |
|-|-|
| `before` / `after` 不是 list | E2202 |
| 两者长度不等 | E2203 |
| `before` 为空 | E2204 |

派生属性：`len(rs)` = 规则条数；`rs.unique_before` = `before` 去重后的条数（T0.2 全量词库为 304,255 条 / 去重 243,535 条，重复 60,720 条）。

**构造入口**

| 方式 | 用法 | 说明 |
|-|-|-|
| 内存数组 | `RuleSet(["甲"], ["乙"])` | 直接给两个等长数组 |
| 词库产物 | `RuleSet.from_files(before_path, after_path)` | 读 T0.2 的 `build/dictionary/rules/before.json` + `after.json`；文件缺失 → E2201，非 UTF-8 / 非合法 JSON / 非字符串数组 → E2202 |

`from_files` 会**主动拒绝对象数组**（如 `[{"before":"甲","after":"乙"}]`），因为 Go 侧 `json.Unmarshal` 到 `[]string` 会直接失败——把错误提前到 Python 侧，报错信息更明确。

### 2.3 `EngineRequest` —— 一次替换的完整描述

| 字段 | 类型 | 默认 | 必填条件 | 说明 |
|-|-|-|-|-|
| `rules` | `RuleSet` | — | 总是 | 用哪套规则 |
| `count` | `int` | `2` | — | 替换趟数，**必须为正整数**（bool 也拒） |
| `input_mode` | `InputMode` | `memory` | — | 文本从哪来 |
| `input_data` | `bytes \| str` | `None` | `input_mode=memory` 时必填 | 内存输入；`str` 按 `encoding` 编码后落临时文件 |
| `input_path` | `Path` | `None` | `input_mode=file / in_place` 时必填 | 文件输入；集成层复制到临时工作区 |
| `output_mode` | `OutputMode` | `memory` | — | 结果怎么交 |
| `output_path` | `Path` | `None` | `output_mode=file` 时必填 | 结果落盘路径；父目录不存在会自动创建 |
| `encoding` | `str` | `utf-8` | — | **仅接受 utf-8**（大小写、连字符形式均可，如 `UTF-8`）；其它即 E2301 |
| `timeout_s` | `float` | `300.0` | — | 子进程超时秒数，必须 > 0 |
| `protocol` | `str` | `fixtext-engine/1` | — | 协议版本 |

**枚举取值**

| 枚举 | 取值 | 语义 |
|-|-|-|
| `InputMode` | `memory` | 调用方给 str/bytes，集成层落临时文件 |
| | `file` | 调用方给路径，集成层读入后落临时副本 |
| `OutputMode` | `memory` | 结果读回内存，原始输入不动 |
| | `file` | 结果写到 `output_path`，原始输入不动 |
| | `in_place` | 结果覆盖 `input_path`（显式 opt-in，原文件不可恢复） |

**`validate()` 的静态校验矩阵**（全部在起子进程之前判定，命中即 E2301，除规则类错误外）

| # | 条件 | 错误码 |
|-|-|-|
| 1 | `protocol != PROTOCOL_VERSION` | E2301 |
| 2 | `count` 非 int / 是 bool / `<= 0` | E2301 |
| 3 | `encoding` 归一化后不是 `utf8` | E2301 |
| 4 | `timeout_s` 非数值 / `<= 0` | E2301 |
| 5 | `input_mode=memory` 但 `input_data is None` | E2301 |
| 6 | `input_mode=file/in_place` 但 `input_path is None` | E2301 |
| 7 | `output_mode=file` 但 `output_path is None` | E2301 |
| 8 | `output_mode=in_place` 但 `input_mode != file` | E2301 |
| 9 | `rules.validate()` 抛出的 E2202 / E2203 / E2204 | 原样上抛 |

### 2.4 `EngineResult` —— 成功结果摘要

`as_dict(include_text=False)` 序列化后的字段（全部为实测值，无外推）：

| 字段 | 类型 | 说明 |
|-|-|-|
| `bytes_in` / `bytes_out` | `int` | 输入 / 输出字节数 |
| `chars_in` / `chars_out` | `int` | 按 `encoding` 解码后的字符数；解码失败记 `-1` |
| `sha256_in` / `sha256_out` | `str` | 输入 / 输出 SHA-256（十六进制小写） |
| `rules` | `int` | 本次使用的规则条数 |
| `unique_rules` | `int` | `before` 去重后的条数 |
| `count` | `int` | **引擎自报**的替换趟数（已与请求核对） |
| `elapsed_s` | `float` | 子进程 wall time，保留 4 位小数 |
| `exit_code` | `int` | 恒为 0（非 0 走错误分支） |
| `engine_stdout` | `str` | 引擎 stdout 全文（strip 后），通常只有一行摘要 |
| `engine_path` | `str` | 实际执行的引擎绝对路径 |
| `changed` | `bool` | `bytes_in != bytes_out`；无命中时为 `False` 且 `sha256_in == sha256_out` |
| `output_text` | `str \| None` | **仅 `include_text=True` 时出现**；`output_mode=memory` 时为解码后的全文，否则 `None` |

`output_text` 默认不序列化，是为了避免把整本小说塞进日志 / 评论；`request_to_dict()` 同理，只留 `input_sha256` 与 `input_bytes`，不留正文。

### 2.5 `EngineResponse` —— 统一响应

| 字段 | 类型 | 说明 |
|-|-|-|
| `protocol` | `str` | 回显 `fixtext-engine/1` |
| `ok` | `bool` | 成功与否 |
| `result` | `EngineResult \| None` | `ok=True` 时必非空 |
| `error` | `EngineError \| None` | `ok=False` 时必非空 |

`result` 与 `error` **互斥**，构造时即断言（`__post_init__`），防止出现"既 ok 又带 error"的模糊状态。构造入口：`EngineResponse.success(result)` / `EngineResponse.failure(error)`。

`as_dict()` 输出形状：

```json
{
  "protocol": "fixtext-engine/1",
  "ok": true,
  "result": { "...": "见 2.4" },
  "error": null
}
```

### 2.6 `EngineError` —— 带码异常

| 字段 | 类型 | 说明 |
|-|-|-|
| `code` | `str` | 机器可读错误码（见第三节），调用方**按码分流，不解析自然语言** |
| `message` | `str` | 人类可读说明（中文），异常字符串形如 `[E1003] 引擎调用超时（0.6s）…` |
| `detail` | `dict` | 现场证据：引擎路径、完整命令数组、超时值、`stdout_tail` / `stderr_tail` 尾部 |

派生只读属性：`error.name`（如 `ENGINE_TIMEOUT`）、`error.remedy`（建议处置）；`error.as_dict()` 输出 `{code, name, message, remedy, detail}` —— `remedy` 从错误码目录取，保证同一码在任何调用点的处置建议一致。

### 2.7 调用形态速查

```python
from fixtext.engine import EngineRequest, GoEngineClient, OutputMode, RuleSet

rules = RuleSet.from_files("rules/before.json", "rules/after.json")
client = GoEngineClient()  # 默认用 builder.ensure_engine() 的产物

# A. 内存进、内存出（最常用于测试与短文本）
resp = client.run(EngineRequest(rules=rules, input_data="甲甲", count=2))
if resp.ok:
    print(resp.result.sha256_out, resp.result.output_text)
else:
    print(resp.error.code, resp.error.remedy)

# B. 文件进、文件出（原文件不动）
resp = client.run(
    EngineRequest(
        rules=rules,
        input_mode=InputMode.FILE,
        input_path="novel.txt",
        output_mode=OutputMode.FILE,
        output_path="out/novel.txt",
        count=2,
        timeout_s=300,
    )
)

# C. 文件进、原地覆盖（显式 opt-in）
resp = client.run(
    EngineRequest(
        rules=rules,
        input_mode=InputMode.FILE,
        input_path="novel.txt",
        output_mode=OutputMode.IN_PLACE,
        count=2,
    )
)
```

`GoEngineClient(engine_path=None, default_timeout_s=300.0)`：`engine_path` 省略时按当前主机解析 `go_src/bin/replace_by_go-<goos>-<goarch>[.exe]`。**构造期不抛错**——引擎缺失信息留到 `run()` 时归成 E1001，便于调用方先建 client 再统一处理错误。

## 三、错误码定义

分段规则：`E1xxx` 引擎进程层，`E2xxx` 入参层，`E1900` 兜底。字符串码是稳定契约，**不得改名**。

| 错误码 | 名称 | 含义 | 典型触发条件 | 建议处置 | 已实测 |
|-|-|-|-|-|-|
| `E1001` | ENGINE_MISSING | 引擎可执行文件不存在 | 未构建 / `engine_path` 指错 / 路径被删 | `python -m fixtext.engine.builder` 离线构建，或用 `engine_path` 指向已有二进制 | 是 |
| `E1002` | ENGINE_NOT_EXECUTABLE | 文件在，但跑不起来 | 无 `x` 位；路径是目录；`Exec format error`（架构/平台不符，如拿 Windows 二进制在 Linux 上跑） | `chmod +x`；确认目标平台与主机一致 | 是（两种触发） |
| `E1003` | ENGINE_TIMEOUT | 调用超时，子进程已被 kill | `timeout_s` 小于实际耗时（1 核 + 大语料 + 30 万条规则极易命中） | 调大 `timeout_s`；按 1 核环境预估两趟替换耗时 | 是 |
| `E1004` | ENGINE_FAILED | 非 0 退出，但 stderr 未命中任何已知文案 | 引擎被改动 / 新增了未登记的错误分支 | 读 `detail.stderr_tail`，补一条归类规则到 `_STDERR_RULES` | 否（被下面更具体的码覆盖） |
| `E1005` | ENGINE_OUTPUT_UNEXPECTED | 退出码 0 但 stdout 不合协议 | 引擎被换成空实现 / 改了输出文案；自报次数与请求不符；输出非 UTF-8 | 重新对齐协议（见第一节） | 是 |
| `E1900` | ENGINE_UNKNOWN | 未归类的 OSError | 集成层自身漏归类的异常路径 | 保留 `detail` 现场并补归类 | 否 |
| `E2101` | INPUT_MISSING | 待替换文件不存在 | `input_path` 拼错 | 检查路径 | 是 |
| `E2102` | INPUT_UNREADABLE | 文件在但读不出 | 路径是目录；权限不足；被独占 | 查权限与占用 | 是 |
| `E2201` | RULES_MISSING | 规则文件不存在 | T0.2 产物路径错 | 确认 `rules/before.json` 与 `rules/after.json` | 是（`from_files` 路径） |
| `E2202` | RULES_INVALID_JSON | 规则不是合法 JSON 字符串数组 | 非 UTF-8 / 语法错 / 对象数组 / 顶层不是数组 | 重新导出词库；不要手工改 JSON | 是 |
| `E2203` | RULES_LENGTH_MISMATCH | before / after 条数不等 | 词库导出中断、只更新了一侧 | 回 T0.2 链路重新导出，逐条对齐 | 是 |
| `E2204` | RULES_EMPTY | 规则集为空 | 传空数组 | 至少给一条；空规则集不算一次有意义的替换 | 是 |
| `E2301` | ARGUMENT_INVALID | 调用参数非法 | `count<=0`；协议版本不符；编码不是 UTF-8；`timeout_s<=0`；输入/输出模式与实参不匹配 | 按 2.3 的校验矩阵核对 | 是 |
| `E2401` | OUTPUT_WRITE_FAILED | 结果落盘失败 | 输出父路径是文件而非目录；无写权限；磁盘满 | 查输出目录是否存在可写 | 是 |

### 3.1 stderr 文案 → 错误码映射

引擎自身把细节打在 stderr 上，集成层**不吞原始信息**：原始 stderr 全文保留在 `detail.stderr_tail`，同时按下列规则（`errors._STDERR_RULES`，顺序敏感，更具体的在前）归类成码。

| stderr 包含 | 归类为 |
|-|-|
| `规则数量不匹配` | E2203 |
| `替换规则为空` | E2204 |
| `JSON 解析失败` | E2202 |
| `读取替换前规则` / `读取替换后规则` | E2201 |
| `读取文件失败` | E2102 |
| `替换次数必须` / `参数数量错误` | E2301 |
| `写入文件失败` | E2401 |
| （都不匹配） | E1004 |

## 四、离线构建

### 4.1 前提（T0.3a 盘点结论，已由 `builder.check_zero_external_deps()` 在构建前自检）

- 引擎源码只有 1 个文件 `go_src/replace_by_go.go`，import 恰好 5 个标准库：`encoding/json`、`fmt`、`os`、`strconv`、`strings`；
- 包内**无 go.sum / go.work**（有则拒绝构建）；
- import 里出现任何带点号的第三方模块（如 `github.com/...`）→ 拒绝构建（E2301）。

### 4.2 构建命令

```bash
# 当前主机（Linux）
python -m fixtext.engine.builder

# 显式指定 Windows 交叉编译（不用 mingw / gcc）
GOOS=windows GOARCH=amd64 CGO_ENABLED=0 GOPROXY=off GOTOOLCHAIN=local \
  go build -p 1 -trimpath -o bin/replace_by_go-windows-amd64.exe replace_by_go.go

# 一次编两个目标
python -m fixtext.engine.builder --both
```

构建环境由 `builder.offline_env()` 统一固定：

| 变量 | 值 | 作用 |
|-|-|-|
| `GOPROXY` | `off` | **禁网**：任何需要下载模块的场景立即失败，而不是偷偷联网 |
| `GOTOOLCHAIN` | `local` | 禁止按 go.mod 里的版本号自动下载新工具链 |
| `GOFLAGS` | `-mod=mod` | 不依赖 vendor 目录 |
| `CGO_ENABLED` | `0` | 纯 Go 静态链接；Windows 交叉编译无需 C 工具链 |
| `GOWORK` | `off` | 忽略上层 go.work，避免被外部 workspace 影响 |
| `-p 1` | 固定 | 1 核沙箱，串行编译，不抢占内存 |

产物落在 `src/fixtext/engine/go_src/bin/replace_by_go-<goos>-<goarch>[.exe]`，文件名带平台后缀，便于多平台二进制共存。

### 4.3 Windows 侧注意

- `chmod_executable()` 对 `.exe` 直接跳过（Windows 无执行位概念）；
- `_resolve_engine()` 的 `os.access(path, os.X_OK)` 检查在 `os.name == "nt"` 时跳过；
- Windows 二进制在 Linux 上跑会得到 E1002（`Exec format error`），这是**预期行为**，不是集成层缺陷；反之亦然。

### 4.4 构建耗时（1 核沙箱实测）

| 目标 | 耗时 | 产物大小 |
|-|-|-|
| linux-amd64 | 0.25 s | 2,646,016 B |
| windows-amd64 | 0.25 s | 2,763,776 B（PE 头 `MZ`） |

## 五、调用方必须知道的边界

1. **本层不含替换语义**。Python 侧不做任何字符串替换，只做进程调度与校验。想要 Python 版语义，属 M1。
2. **`count` 由引擎执行，不由 Python 循环**。`count=2` 是引擎内部跑两趟 `Replacer.Replace`，链式收敛效果（`甲→乙`、`乙→丙` 时输入「甲」输出「丙」）来自引擎，不是集成层拼接。
3. **替换是"整串一次扫"**。`strings.NewReplacer` 是首胜/最长匹配优先、不重叠：规则 `["ABC","AB"] → ["1","2"]` 对输入 `ABABC` 输出 `21`（`ABC` 先吃掉前三个字符）。集成层不改变这一行为，测试已固定该语义。
4. **超时是硬 kill**。`subprocess.run(timeout=...)` 到期即 SIGKILL，引擎没有机会清理；因此临时工作区一定在 `finally` 里删除，且原文件从不交给引擎。
5. **本层不负责批量调度**。多文件替换由上层循环发 `EngineRequest`；`ReplacementBatch` 只是给上层对齐错误用的轻量记录结构，不含并发实现。
