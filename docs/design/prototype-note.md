# 原型说明 · 原型与实现的关系

> 本页说明 `docs/design/` 里收了什么、没收什么，以及这些文件与仓库里产品代码的关系。读原型前先看这一页，能避免把它当成第二套实现。

## 一句话结论

**`docs/design/prototypes/` 是本产品的 UI 设计事实源**——界面长什么样、每个页面有哪些状态、交互怎么走，以原型为准。产品代码 `fixtext_ui/` 是这份设计的落地实现，两者不是并列的两套方案。

## 怎么看这些原型

- **只想看界面和交互**：直接打开 `prototypes/FixTextGUI_合并版_原型.html`，单文件、无外部依赖，浏览器双击即可。七个模块都在里面，可以从导入一路点到导出。
- **只想看某一页**：打开对应的单模块原型，比合并版更容易对照。
- **要查某个颜色、字号、圆角的取值**：一律看 `prototypes/FixTextGUI_设计系统_薄地基.html` 的 `:root`。这个 `:root` 是唯一源，其他原型把令牌逐字复制进自身，仅为离线预览方便，不作为取值依据。
- **想知道某个界面决策为什么这么定**：看 `prototypes/FixTextGUI_设计决策_导航与令牌统一.md`。

## 为什么 `src/` 的 PySide 骨架不入库

原型期还写过一套 PySide6 骨架（`src/` 下的 `main_window.py`、`fixtext_widgets.py` 等 12 个模块，以及 `tests/` 下 9 个冒烟与截图脚本）。**它不入库**，原因有三条：

1. **已被取代**。产品代码 `fixtext_ui/` 是从这套骨架长出来的正式实现，功能更全（真实导入链路、后台线程、进度与取消、错误中心、导出与历史快照），骨架停在原型期状态。两套代码同时进公开仓库，最容易造成的误读就是"这个项目有两套 UI 实现，我该改哪一套"。
2. **会与产品代码冲突**。骨架与产品代码共用同一批模块名（`main_window.py`、`fixtext_widgets.py`、`fixtext_tokens.py`、`import_module.py` 等），目录不同但名字相同，检索与跳转都会指向错的那一份。
3. **它的价值已经转移**。骨架真正值得留下的东西——令牌取值、控件形态、交互节奏——都已固化进原型 HTML 与设计系统文件；骨架剩下的部分是可运行的胶水代码，读它不如读产品代码。

同理，**`src/*.py`、`tests/*.py` 与 `__pycache__` 一并排除**。`tests/` 下那几个脚本是骨架期的冒烟与截图验证，与仓库 `tests/` 里的正式测试同名不同物，混在一起会让"测试为什么有两套"的问题无解。

## `fixtext.qss` 为什么只保留原型期那一份

`docs/design/fixtext.qss` 是原型期的样式表快照（273 行 / 59 个规则块），用于说明"令牌如何展开成 QSS"这一层设计意图。仓库里产品实际使用的样式表在 `fixtext_ui/fixtext.qss`（1369 行 / 364 个规则块），是它的后续演进版——多出来的部分是产品化过程中新增的控件与状态。**要改样式，改产品那份；这里这份只作设计参考，不要再往里加规则。**

## 文件命名

本目录内所有文件名前缀统一为 `FixTextGUI_`，与仓库当前的产品显示名一致。原型文件正文里的界面文案、截图里的窗口标题保留了原型期原样，因此个别地方仍能看到旧的产品名——那是设计过程中的历史痕迹，不是待修项。

## 不在本目录的内容

| 排除项 | 原因 |
|---|---|
| UI 目录整包 zip | 与目录内文件完全重复，26 MB 无增量信息 |
| `icons/` 整个目录（30+ SVG 与两个 preview 页） | 图标资源属独立分支维护，不进主干文档 |
| 合并版原型的旧版本（旧 HTML 与旧更新记录各一份） | 已被新版逐字取代，保留只会造成同名文件歧义 |
| `src/*.py`、`tests/*.py`、`__pycache__` | 见上文「为什么骨架不入库」 |
| 骨架期截图 | 界面已由原型 HTML 与产品自身表达，截图无法索引也不便维护 |
