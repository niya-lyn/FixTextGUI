### A2 · 异常路径有错误码：引擎进程缺失、调用超时，各真实触发一次 —— 通过

11 个异常用例 **11/11 命中预期错误码**（`results/integration_verify.json` → `errors.cases`）。两个卡片点名的路径均为真实触发，非模拟：

**① 引擎进程缺失 → E1001**

```
engine_path = /tmp/fixtext-no-such-engine-binary
code    : E1001
name    : ENGINE_MISSING
message : 引擎可执行文件不存在: /tmp/fixtext-no-such-engine-binary
remedy  : 先执行 python -m fixtext.engine.builder 离线构建，或用 engine_path 指向已有二进制
detail  : {"engine_path": "/tmp/fixtext-no-such-engine-binary",
           "hint": "python -m fixtext.engine.builder 可离线构建"}
```

触发方式：真实指向一个不存在的路径，`_resolve_engine()` 的 `Path.exists()` 判定失败即抛码。

**② 调用超时 → E1003（子进程被真实 kill）**

```
timeout_s      = 0.6
observed_wall  = 0.715 s
corpus         = corpus_fanpai.txt（22.39 MiB 真实语料）
code    : E1003
name    : ENGINE_TIMEOUT
message : 引擎调用超时（0.6s），子进程已被强制终止
remedy  : 调大 timeout_s，或确认当前为 1 核环境、大文件两趟替换预期耗时
detail  : {"timeout_s": 0.6,
           "command": ["…/replace_by_go-linux-amd64",
                       "/tmp/fixtext-engine-4acy73dn/target.txt",
                       "/tmp/fixtext-engine-4acy73dn/before.json",
                       "/tmp/fixtext-engine-4acy73dn/after.json", "2"],
           "stdout_tail": "", "stderr_tail": ""}
```

`observed_wall_s = 0.715` 大于 `timeout_s = 0.6`，证明是**真超时**而非「跑得快所以没超时」。为排除「环境太慢/引擎坏了」这一混淆，同批还跑了一条**对照组**：同样的 304,255 条规则、同样的 22.39 MiB 语料，`timeout_s=300` 时**成功**（3.1 s 量级完成），证明超时归因于超时值本身而非环境。

**③ 其余 9 个异常用例（同样真实触发）**

| 用例 | 期望码 | 实际码 | 触发方式 | 现场要点 |
|-|-|-|-|-|

| `engine-not-executable-no-x-bit` | E1002 | E1002 | 文件存在但 `chmod 644` | `mode: 0o100644` |

| `rules-invalid-json-direct-subprocess` | E2202 | E2202 | 绕过 `RuleSet` 静态校验，把坏 JSON 直接喂给引擎 | 引擎 stderr：`加载规则失败: 读取替换前规则: JSON 解析失败: invalid character 'b' …` |

**错误码覆盖率**：14 个码中，本轮**实际触发 11 个**（E1001 / E1002×2 / E1003 / E2101 / E2202 / E2203 / E2204 / E2301 / E2401 + 成功对照组）。未触发的 3 个及原因：

| 码 | 未触发原因 |
|-|-|
| E1004 ENGINE_FAILED | 是「非 0 退出但 stderr 未命中已知文案」的**兜底码**；本轮所有非 0 退出都带已知文案，故自然落到更具体的码。逻辑上无法「主动制造」——要么引擎改了文案，要么自定义引擎。 |

| E1900 ENGINE_UNKNOWN | 兜底码，用于「出现了没归类的 OSError」。当前所有 OSError 分支均已归入 E1002 / E2102 / E2401，故不触发——**这正是它的设计目的：出现即说明有未归类路径**。 |

E2201 RULES_MISSING 未列入上表，因为它在 `tests/test_engine_protocol.py` 中已被真实触发（`RuleSet.from_files` 指向不存在的文件 → E2201）。

## B · Go 编译流程（离线）

### B.1 零外网依赖已由脚本自检

`builder.check_zero_external_deps()` 在每次构建前解析 `go_src/replace_by_go.go` 的 import 块，并做两项硬判定：

1. 目录内若存在 `go.sum` 或 `go.work` → 拒绝构建（E2301），因为有 go.sum 就意味着引入过外部模块；
2. import 列表中若出现含点号的第三方模块（如 `github.com/...`）→ 拒绝构建。

实测 import 清单（5 个，全部标准库）：

```
encoding/json
fmt
os
strconv
strings
```

### B.2 实际执行的构建命令与产物

构建环境由 `builder.offline_env()` 统一固定：

| 变量 | 值 | 作用 |
|-|-|-|
| `GOPROXY` | `off` | **禁网**：需要下载模块的场景立即失败而非偷偷联网 |
| `GOTOOLCHAIN` | `local` | 禁止按 go.mod 版本号自动下载新工具链 |
| `GOFLAGS` | `-mod=mod` | 不依赖 vendor 目录 |
| `CGO_ENABLED` | `0` | 纯 Go 静态链接，Windows 交叉编译无需 C 工具链 |
| `GOWORK` | `off` | 忽略上层 go.work |
| 编译并行度 | `-p 1` | 1 核沙箱串行编译 |
| 路径信息 | `-trimpath` | 产物不嵌入本机绝对路径，便于分发 |

| 目标 | 实际命令 | 耗时 | 产物大小 | 校验 |
|-|-|-|-|-|
| linux-amd64 | `go build -p 1 -trimpath -o bin/replace_by_go-linux-amd64 replace_by_go.go` | 0.183 s | 2,646,016 B | ELF，退出码 0 |
| windows-amd64 | 同上（`GOOS=windows GOARCH=amd64`） | 0.142 s | 2,763,776 B | **PE 头 `4d5a`（MZ）**，退出码 0 |

Go 工具链版本：`go version go1.22.8 linux/amd64`（沙箱预装）。

### B.3 Windows 交叉编译方法

```bash
# 在 Linux/macOS 上交叉编译 Windows 版本（不需要 mingw / gcc，纯 Go + CGO_ENABLED=0）
GOOS=windows GOARCH=amd64 CGO_ENABLED=0 GOPROXY=off GOTOOLCHAIN=local GOWORK=off \
  go build -p 1 -trimpath -o bin/replace_by_go-windows-amd64.exe replace_by_go.go
```

或用工程脚本（等价，带零依赖自检与产物校验）：

```bash
python -m fixtext.engine.builder --windows     # 只编 Windows 目标
python -m fixtext.engine.builder --both        # 当前主机 + Windows 两个目标
python -m fixtext.engine.builder --goarch=386  # 需要 32 位目标时
```

Windows 侧注意：`chmod_executable()` 对 `.exe` 跳过；`_resolve_engine()` 的 `os.access(X_OK)` 检查在 `os.name == "nt"` 时跳过。**Windows 二进制在 Linux 上跑会得到 E1002**（`Exec format error`），这是预期行为而非缺陷。

### C.3 一次「假通过」的排查记录

首轮自验曾出现 `equivalence_has_20mb: true` 却实际没验到 20MB 切片的情况，原因是脚本把 corpus 文件名按 key 拼成 `corpus_slice20mb.txt`，而实际文件名是 `corpus_20mb_slice.txt`，切片用例被静默跳过；同时 20MB 判定条件写成「任一语料 ≥20MiB」，被 22.39 MiB 的 `fanpai` 全文顶成 True。修复两处后重跑，判定条件收紧为「**切片语料本身** ≥20 MiB」，才得到上表的真实结果。**这次假通过说明：判定条件必须指向被验对象本身，不能用邻近对象顶替。**
